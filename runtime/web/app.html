      1. Connect your telemetry provider

      Choose your existing monitoring platform. One source supplies metrics for multiple services; individual application API keys are not needed. This beta uses one active source at a time.

      Use the Prometheus server URL, reachable from CoRCA.

      Queries must return one series per service, grouped by this label.

      Coarser metrics require longer diagnosis windows.

      Enter the variable’s name, never the API key itself. Your administrator sets its value on the CoRCA server.

      Adapt the examples to your metric names and labels. Add latency and error metrics when available.

      Administrator connection notes

      Load calibration for this method before enabling the Alertmanager receiver.

      For a remote private endpoint, allow its hostname with CORCA_ALLOWED_SOURCE_HOSTS on the CoRCA server. Connections use read-only queries. Query URLs must not contain credentials.

      A new connection requires matching calibration.

      Saving replaces the active source and clears its calibration. Previously queued diagnoses retain their original source and thresholds.

      Using OpenTelemetry or an agent?

      Keep your existing Datadog, Dynatrace, or New Relic instrumentation and select that provider above. For vendor-neutral instrumentation, send OpenTelemetry metrics through a Collector into Prometheus or Grafana Cloud, then connect that query backend.

      Set a distinct service.name for each application. CoRCA reads historical metric queries; it is not an OTLP ingest endpoint or a logs/traces backend.

      # Application environment (adapt the Collector address)
OTEL_SERVICE_NAME=payments
OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4318
OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
OTEL_METRIC_EXPORT_INTERVAL=15000

      Configure the Collector’s metrics pipeline and a durable metrics backend. If Prometheus labels differ from service.name, choose the actual query label above.

      2. Route alerts from Alertmanager

      Add this receiver to your Alertmanager configuration and route the relevant alerts to corca. Replace the URL if your service uses a different namespace or hostname.

      receivers:
  - name: corca
    webhook_configs:
      - url: http://corca-api.corca.svc:8000/v1/alerts
        send_resolved: false
        http_config:
          authorization:
            type: Bearer
            credentials_file: /etc/alertmanager/corca-token

      Mount the deployment’s API key at the credentials_file path inside Alertmanager. Set a matching route.receiver; merge with existing routing rather than replacing it. CoRCA diagnoses firing alerts only.

      3. Connect through the API

      Use the deployment API key from a trusted client. Keep keys out of URLs and shared reports.

      Workspace / Guide
      One workflow. Clear responsibilities.
      What your team needs to connect, investigate, and operate this beta.
      
      
      Deployment administrators
      1. Deploy one CoRCA instance with persistent storage and a private network or HTTPS access gateway.
      2. Connect a telemetry provider and discover reporting services.
      3. Confirm dependencies and load calibration fitted to the same telemetry.
      4. Provide the service URL and API key to trusted responders. Mount the key in Alertmanager for automatic diagnoses.
      
      
      Incident responders
      1. Connect using the API key supplied by your administrator.
      2. Start a diagnosis at the first sign of the incident. CoRCA compares healthy and incident windows.
      3. Review candidate causes, explained symptoms, and remaining anomalies.
      4. Cross-check with dashboards and logs. Download a result or share a diagnosis link with your team.
      
      
      Understand the evidence
      • Score share compares anomaly scores; it is not a probability of correctness.
      • Partial results need further investigation. A timeout does not establish that all causes were found.
      • Missing telemetry and an inaccurate dependency graph can hide causes.
      • CPU and memory alone may miss delay faults. Include latency and error metrics where available.
      
      
      Beta access & operating limits
      • This is a shared, single-deployment workspace. Every API key holder has the same access.
      • Individual accounts, SSO, role enforcement, tenant isolation, and an audit trail are not available in this beta.
      • Run behind your organization’s access gateway before sharing outside a trusted team.
      • SQLite supports one service replica. Plan database and identity work before broader enterprise rollout.
